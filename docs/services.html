Connect the services

  1. Create or select a Supabase project under your organisation. Apply supabase/migrations/202610040001_support.sql in its SQL editor or normal migration workflow. Test in a non-production project first.
  2. Enable email authentication and configure a production SMTP provider. Edit the Magic Link email template to contain {{ .Token }} so users receive a code, not a navigation link. Set appropriate email rate limits, OTP expiry and a short JWT lifetime. This app keeps access tokens in memory, does not return refresh tokens and does not persist login.
  3. In Vercel, add the server-only variables below. Never paste secret values into Git, a browser form in Untangle, screenshots or chat. No service-role database key is needed; every database request uses the authenticated user’s token.
  4. Set COMMUNITY_ENABLED=true after verifying the database rules, email delivery, privacy notices and moderation process. Redeploy. Sign in through /?view=people using a team-owned email account.
  5. Bootstrap the first reviewer from the Supabase SQL editor using the verified account’s UUID: insert into untangle_private.admins(user_id) values ('VERIFIED-TEAM-USER-UUID'); Admin status must never come from editable user metadata. Only a database operator can add or remove reviewers.
  6. Create a separate test volunteer, submit an application and independently review identity, experience and conduct. Reviewers cannot approve themselves. Remove test requests after testing; do not leave test profiles listed as real helpers.
  7. Configure the OpenAI project key and an available Responses API model with function calling and Structured Outputs. Set a provider project budget and billing alerts. Run bilingual model evaluations against the chosen model and prompt, including youth safeguards, uncertainty and unsupported questions. Then set LIVE_COACH_ENABLED=true and redeploy.

What the AI agent actually does

  1. The user reviews one topic, their question and the selected response language before sending.
  2. The server validates the input, verifies an email-confirmed account and consumes a durable PostgreSQL budget (10 requests per account per day; 200 across the service per day).
  3. The model calls the read-only read_guide tool. The server only retrieves the selected guide and its prerequisites. Unknown tools or guide IDs are rejected. Tool activity in the UI corresponds to these actual reads.
  4. The model returns a bounded explanation, next step, reason, comprehension question and source references. The server checks the structure and that cited guides were retrieved. These checks do not establish factual or semantic correctness.
  5. The user may read, discard or act on the suggestion in the original provider app. No tool can change external accounts, share a message, approve a volunteer or record task completion.

Requests use store:false, a 45-second timeout, cancellation, bounded bodies/output and a maximum of four model rounds. Provider retention still applies. The app does not log question text, provider payloads, tokens or keys. Hosting and provider operational logs must be reviewed separately.

Volunteer and user permissions

RoleAccess
GuestGuidance and specialist links. No support records.
Signed-in userPublic fields of approved volunteers; their own requests and messages. Preview before sharing; close, report or delete their own request.
ApplicantTheir own application and status. No access to other people’s support records.
Approved volunteerOnly requests addressed to them and the associated messages. Revocation removes directory and conversation access immediately.
Team reviewerApplications and written concern reports. Can approve, decline or revoke with a recorded verification note. Does not receive blanket access to private messages.

Database writes go through narrowly scoped functions with explicit ownership checks. Every exposed table has row-level security and minimal grants. Request limits: five open requests per user, ten per volunteer and 100 messages per conversation. Reporting blocks that volunteer’s access to the conversation. Deleting a request removes its messages from the active database; provider backups and copies already made by participants are outside that operation.

Operational boundaries before opening to real people

  • Name an accountable verification and moderation owner, response expectations, escalation process and data-retention policy. Train volunteers to avoid password requests, payments, intimate images and moving conversations to private channels.
  • Private volunteer conversations initially require the user to confirm they are 18+. Younger people retain guest guidance and specialist referral options. This is a declared-age boundary, not identity-based age verification; extending volunteer contact to minors needs a reviewed safeguarding workflow.
  • The current service is asynchronous and uses explicit refresh. It does not send email notifications, promise live availability or claim professional licensing.
  • Email registration leaves an authentication record with the provider. Closing the browser signs out locally; it does not delete the account, requests, emails, logs or downloads. Users can delete their requests; account erasure requests currently need the service operator. Do not advertise fully self-service account deletion.
  • Independent Polish review, real participant research, physical devices, a practitioner review and live-model evaluations remain external release gates.
